# 计算机网络与前后端通信

> 核心主线：
>
> **应用层协议规定“怎么说话” → 传输层负责“怎么传” → 网络层负责“送到哪里” → 数据链路层负责“这一跳怎么送” →
物理层负责“真正变成信号传出去”。**

---

## 1. 协议

**协议（Protocol）**可以理解为通信双方共同遵守的一套规则。

它规定：

* 消息的组织方式
* 消息内容的含义
* 发送方是谁、接收方是谁
* 定义通信的成功和失败，以及失败后的处理方式

例如：

* **HTTP**：规定发送方（Web 客户端）和接收方（服务器）怎么交流
* **TCP/UDP**：规定数据传输是否可靠（建立连接丢包重传保证顺序/不建立连接直接发）
* **IP**：规定如何寻址和进行网络间转发
* **ARP**：帮助在局域网中根据 IP 找到对应的 MAC 地址

所以：

> **协议 ≈ 通信双方共同遵守的“语言规则”。**

---

# 2. OSI 七层模型

OSI 模型把网络通信抽象成七层：

| 层 | 名称    | 主要解决什么          |
|---|-------|-----------------|
| 7 | 应用层   | 应用程序之间怎么交流      |
| 6 | 表示层   | 数据如何表示、编码、加密、压缩 |
| 5 | 会话层   | 管理通信会话          |
| 4 | 传输层   | 端到端的数据传输        |
| 3 | 网络层   | 寻址、路由           |
| 2 | 数据链路层 | 相邻设备之间如何传输      |
| 1 | 物理层   | 真正传输比特的物理信号     |

重点记三个：

```text
HTTP    → 应用层
TCP/UDP → 传输层
IP      → 网络层
```

---

# 3. 实际网络模型（TCP/IP 模型）

实际互联网开发中，经常使用 TCP/IP 模型，而不是严格使用 OSI 七层模型。

可以简单理解成：

```text
HTTP（应用层）
 ↓
TCP / UDP（传输层）
 ↓
IP（网络层）
 ↓
Wi-Fi / Ethernet（网络接口层）
 ↓
电信号 / 无线信号（物理介质）
```

> OSI 七层更多是一种**理解网络的理论模型**，现实协议并不会严格一层对应一个协议。

---

# 4. 数据的传输封装

## 封装（Encapsulation）

发送数据的时候：

```text
应用层：（HTTP 数据）
            ↓ 加 TCP 头
传输层：（TCP 头 + HTTP 数据）
            ↓ 加 IP 头
网络层：（IP 头 + TCP 头 + HTTP 数据）
            ↓ 加链路层头部
数据链路层：帧头 + IP 包 + 帧尾
            ↓ 二进制数据
物理层：电信号 / 光信号 / 无线信号
```

接收端则反过来（**解封装**）：

```text
物理信号
 ↓
数据链路层拆帧
 ↓
网络层处理 IP
 ↓
传输层处理 TCP/UDP
 ↓
应用层解析 HTTP
 ↓
应用程序得到真正的数据
```

# 5. HTTP介绍

> **HTTP：HyperText Transfer Protocol，超文本传输协议**

**应用层协议**：规定客户端和服务器之间如何交流，是一套公开的通信规则。

例如，客户端发送：

```http
GET /api/user/123 HTTP/1.1
Host: example.com
```

服务器返回：

```http
HTTP/1.1 200 OK
{
    "name": "Tom"
}
```

## HTTP 请求方法

```text
GET
POST
PUT
DELETE
HEAD
OPTIONS
...
```

### 状态码

```text
200 → 成功
301/302 → 重定向
400 → 请求错误
401 → 未认证
403 → 禁止访问
404 → 找不到资源
500 → 服务器错误
```

### 请求头

例如：

```text
Host
Content-Type
Authorization
Cookie
User-Agent
...
```

### 响应头

例如：

```text
Content-Type
Content-Length
Set-Cookie
Cache-Control
...
```

### 基本任何编程语言都可以实现 HTTP

```text
HTTP 标准
   ↓
各个程序员/公司按照标准实现
   ↓
Java HTTP 库
Python HTTP 库
Android HTTP 库
浏览器
Spring
Nginx
...
```

## HTTP 和 HTTPS

HTTP 数据通常是明文传输，HTTPS 可以简单理解：

```text
HTTP
 ↓
TLS
 ↓
TCP
 ↓
IP
```

TLS 提供：

* 加密
* 防止数据被篡改
* 服务器身份验证

> **所以 HTTPS ≈ HTTP + TLS**

---

## TLS

> **TLS：Transport Layer Security（传输层安全）**，TCP 之上、应用层之下的安全协议，前身是 SSL

**负责保护网络通信：**

**① 保密**：别人截获数据，也不能直接看懂。

**② 防篡改**：防止数据在传输过程中被偷偷修改。

**③ 身份验证**：帮助确认连接的服务器确实是要访问的服务器。

# 6. TCP 和 UDP介绍

> **传输层协议**：主要解决从一个程序传出的数据，如何被另一个程序接收

**TCP 强调可靠性，确保数据不丢包：**

* 建立连接，三次握手，四次挥手
* 数据确认
* 重传
* 顺序控制、流量控制等

**UDP不提供可靠传输机制，确保低延迟：**

特点：

* 无连接
* 开销小、延迟低
* 不保证一定到达、不保证顺序

### TCP 三次握手与四次挥手

> 在真正传输数据之前，客户端和服务器需要通过**三次握手**建立 TCP 连接

三次握手才能确认彼此的发送和接收能力正常，TCP 建立连接之后，双方就可以传数据：

```
客户端                              服务器
  │                                  │
  │──── SYN ────────────────────────>│      （双方都确认：客户端有发送能力）
  │                                  │
  │<─── SYN + ACK ───────────────────│      （双方都确认：服务器有发送能力 + 接收能力）
  │                                  │
  │──── ACK ────────────────────────>│      （双方都确认：客户端有接收能力）
  │                                  │
  │        TCP连接建立                │
  │                                  │
  │──── 数据 ────────────────────────>│
  │<─── ACK ─────────────────────────│
```

> 通信结束时，需要**四次挥手**关闭连接

```
客户端                              服务器
  │                                  │
  │──── FIN ────────────────────────>│      （双方确认：客户端结束发送）
  │                                  │
  │<─── ACK ─────────────────────────│      （双方确认：服务器结束接收，同时加紧发完剩余内容）
  │                                  │
  │<─── FIN ─────────────────────────│      （双方确认：服务器结束发送）
  │                                  │
  │──── ACK ────────────────────────>│      （双方确认：客户端结束接收）
  │                                  │
  │          连接关闭                 │
```

### UDP 没有 TCP 那样的三次握手

> UDP 是**无连接传输**，没有 TCP 那样的三次握手

```
客户端                        服务器
  │                            │
  │──── UDP 数据 ──────────────>│
  │──── UDP 数据 ──────────────>│
  │──── UDP 数据 ──────────────>│
```

# 7. WebSocket介绍

> **应用层协议**：HTTP 最大的区别之一，是通信模式不同。


WebSocket建立连接后，可以进行**持续的双向通信**：

```text
客户端 ←→ 服务器（适合实时应用、聊天、通知、状态更新）
```

HTTP属于**一来一回**的通信方式：

```text
客户端 → 请求（用户信息）
服务器 → 响应（JSON）
```

# 9. 网络层与数据链路层介绍

数据链路层主要解决：

> 数据链路层主要解决**相邻网络设备之间怎么传数据**

例如：

```text
电脑
 ↓
路由器 A
 ↓
路由器 B
 ↓
路由器 C
 ↓
服务器
```

这就是一条链路。

常见概念：

* MAC 地址
* Frame（数据帧）
* Ethernet（以太网）
* Wi-Fi
* ARP 等相关机制

### ARP

> **ARP：Address Resolution Protocol，地址解析协议**

作用：已知目标 IP 地址，获取目标设备对应的 MAC 地址

```text
IP 地址
 ↓ ARP
MAC 地址
```

因此 ARP 和数据链路层密切相关，但严格划分时，它并不完全等同于传统 OSI 二层协议。

---

### MAC 地址

> **MAC 地址：网络接口在局域网通信中的链路层地址**

```text
MAC → 主要用于一跳通信
IP  → 用于网络间寻址和路由
```

---

### 路由器

路由器根据 IP 和路由表决定数据报在不同网络之间的转发

例如：

```text
局域网
   ↓
路由器
   ↓
互联网
   ↓
服务器所在网络
```

---

### 交换机

> 交换机主要在需要连接很多有线设备时扩展网络

交换机会更新本地设备MAC地址与交换机端口的映射，收到一个帧以后，根据目标 MAC 地址决定帧应该从哪个端口发出去：

```text
电脑 A ─┐
电脑 B ─┼─ 交换机
电脑 C ─┘

电脑A的MAC地址 → 端口 1
电脑B的MAC地址 → 端口 2
电脑C的MAC地址 → 端口 3
```

> WIFI、网线都可以将设备连接到路由器，家用路由器往往已经把**路由器 + 交换机 + Wi-Fi**等功能集成在一个设备里，不需要买交换机

# 10. 前后端应用程序通信介绍

例如一个前端页面请求用户信息：

```text
前端发起请求
  ↓
HTTP GET                 （HTTP的请求方法，底层：HTTP → TCP → IP → 链路层 → 物理层）
  ↓
/api/user/123            （Web后端程序的API路径）
  ↓
执行后端 Controller 方法   （SpringMVC通过API匹配到@GetMapping）
  ↓
业务逻辑                   （增删改查）
  ↓
数据库                     （后端服务与数据库程序通信）
  ↓
返回数据                   （JSON）
  ↓
HTTP Response             （HTTP → TCP → IP → 链路层 → 物理层）
  ↓
前端渲染数据
```

> **前后端通信最常见的应用层协议就是 HTTP/HTTPS。**

本地前后端也可以使用 HTTP（数据实际上没有离开电脑）：

```text
前端：localhost:3000
  ↓
前端请求：http://localhost:8080/api/user      （HTTP → TCP → IP → 本机回环网络 → 后端程序）
  ↓
后端：localhost:8080
```

# 11. 游戏通信方式

> **UDP/TCP 负责传输 + 游戏自定义的数据协议（负责表达玩家位置、玩家方向、操作状态等）**

例如多人游戏：

```text
玩家 A   
 ↓
游戏服务器接收（判断、更新游戏状态）
 ↓
广播给其他玩家
```

# 12. 微信通信方式

> 大量服务器共同承担**连接、消息路由、存储、推送**等工作（大量服务器组成分布式集群）

大致过程：

```text
A 手机聊天客户端
 ↓
微信服务器
 ↓
找到 B 的连接/消息投递路径
 ↓
B 手机聊天客户端
 ↓
显示“你好”
```

具体使用哪些内部协议和架构属于大型系统的实现细节，不能简单等同于某一个 HTTP 或 WebSocket。
